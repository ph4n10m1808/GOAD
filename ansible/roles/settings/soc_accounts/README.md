# SOC directory identities

The selected GOAD-Light final Windows provisioning play calls this role on its parent DC. It creates `soc_siem` enabled with ordinary Domain Users directory-read permissions, and `soc_soar` disabled without response delegation. Neither is an administrator or a collector software account.

Passwords are generated once by Ansible's native password lookup and stored as mode-0600 files under the selected workspace instance's `.soc-credentials/` directory (parent mode0700). `settings/instance_context` resolves exactly one native instance inventory from the controller input sources and checks its metadata identity/provider; it never uses a host's first-definition `inventory_dir`, which can point to shared lab source. Ambiguous or missing instance context fails before credentials or media are changed. Keep that private workspace state; it is excluded by the existing workspace ignore. Sensitive parameters/no_log prevent password output. The guest stores only protected SID/GUID/password-fingerprint ownership receipts. Repeated runs preserve existing passwords, groups, enabled states and ACLs; mismatches fail instead of silently adopting/resetting an existing identity.

Legacy `soc-siem`/`soc-soar` accounts cause a deliberate migration error before underscore identities are created. Do not delete/rename an existing account or copy an old password automatically. If controller credentials are lost, recover them from operator storage; generating a new secret cannot validate the existing account.

This role does not enable AD Entity Analytics or SOAR response. Later approved integration must validate LDAPS CA, actual identity and required delegation. Enabled Windows local event collection uses the Agent's own service permissions, not this AD password. Source preparation alone does not create accounts. The separate 17 November acceptance verified these identities on the rebuilt lab; a new instance still requires its own ownership/readback checks.
